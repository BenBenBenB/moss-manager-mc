Moss Manager — Manual test plan

Tracks the command tree defined in docs/commands.md. Check each row as you verify it; state persists in your browser's localStorage under the key mossman-test-plan-v4.

Setup

  1. Run ./gradlew :fabric:runClient from the repo root.
  2. Create a new single-player world with cheats enabled.
  3. World folder default: run/saves/<world-name>/. Project files land at <world>/mossmandata/projects/<id>.json.
  4. Names are user-facing identifiers; ticket numbers are per-project integers visible in /mossman ticket list <projectId>. Tab-completion suggests every valid value from the current project — exercise it as you go.

Optional: a second client on the same LAN for the multi-player rows below. All other commands work solo.

Successful commands print white text (sendSuccess); failures print red (sendFailure).

Round 1 — Project commands

#CommandExpected
1.1 /mossman project list No projects you can view.

1.3 /mossman project create alpha Dup project already exists: alpha

Don't delete alpha yet — Rounds 2–5 need it.

Round 2 — Role commands

Targeting by case-insensitive name. Tab-completion suggests existing roles after you type the project ID.

#CommandExpected
2.1 /mossman project config role list alpha Lists Default, Viewer, Editor, Admin (default pinned at index 0; higher index = higher priority). Each row has a [view] button.
2.2 /mossman project config role view alpha Admin Header, hex color, sorted Permissions list, member count
2.3 /mossman project config role create alpha Reviewer Created role Reviewer with default color (white) and no permissions
2.4 /mossman project config role create alpha "Senior Reviewer" {color:0xFFAA00, grants:["VIEW_PROJECT","VIEW_TICKETS"], denials:["DELETE_TICKETS"]} Created role Senior Reviewer with the supplied color, grants, and denials
2.5 /mossman project config role update alpha Reviewer {name:"Casual Reviewer", color:0x00FFFF} Updated role Reviewer — both fields change (multi-key patch)
2.6 /mossman project config role setpermission alpha "Casual Reviewer" EDIT_TICKETS GRANT Set EDIT_TICKETS for Casual Reviewer → GRANT
2.7 /mossman project config role setpermission alpha "Casual Reviewer" BOGUS GRANT unknown permission 'BOGUS'
2.8 /mossman project config role setpermission alpha "Casual Reviewer" EDIT_TICKETS INHERIT Set EDIT_TICKETS for Casual Reviewer → INHERIT
2.9 /mossman project config role order alpha "Casual Reviewer" 2 Moved role Casual Reviewer to position 2 · role list reflects new order. Default must stay at index 0.
2.10 /mossman project config role order alpha Default 1 cannot reorder the default role; it is pinned at index 0
2.11 /mossman project config role delete alpha "Casual Reviewer" Deleted role Casual Reviewer
2.12 /mossman project config role assign alpha Editor <OtherPlayer> Assigned Editor to <OtherPlayer>
2.13 /mossman project config role unassign alpha Editor <OtherPlayer> Unassigned Editor from <OtherPlayer>

Round 5 — Ticket commands

Tickets are addressed by per-project integer (#1, #2, …) once created. Use /mossman ticket list <projectId> to see numbers; tab-completion on the ticket arg shows each number with the title in the tooltip.

#CommandExpected
5.1 /mossman ticket list alpha No tickets in alpha.
5.2 /mossman ticket create alpha {title:"First bug"} Created ticket #1
5.3 /mossman ticket create alpha (no patch) ticket create requires 'title'
5.4 /mossman ticket create alpha {title:"Big feature", description:"detailed desc", status:"In Progress", type:"Feature"} Created ticket #2
5.5 /mossman ticket view alpha 2 Header, Status: In Progress, Type: Feature, Assignee: (unassigned), description
5.6 /mossman ticket update alpha 1 {title:"Renamed", status:"Done"} Updated ticket #1 — title + status change in one call (multi-field patch fans out to UpdateTicketUseCase + ChangeTicketStatusUseCase internally)
5.7 /mossman ticket update alpha 1 {type:"Bug"} Updated ticket #1 — only type changes; title preserved
5.8 /mossman ticket update alpha 1 {assignee:"<OtherPlayerName>"} Updated ticket #1 · ticket view alpha 1 shows Assignee: <OtherPlayer> with UUID in hover
5.9 /mossman ticket delete alpha 1 Deleted ticket #1. Note: creating another ticket now jumps to #3 — numbers don't get reused.

Round 9 — Backlog rework (denials, template, no-reuse, buttons)

Covers the changes from the multi-item backlog: default project template, role-priority denials, ticket-number no-reuse, optional delete replacement, SNBT boolean, and the in-chat button augmentations.

#CommandExpected
9.1 Boot a fresh world. Inspect <world>/mossmandata/. default.json exists alongside projects/. Hand-edit a status name, restart server.
9.2 /mossman project create p1 First then /mossman project view p1 Statuses reflect the edited template; role/status/type UUIDs are fresh (no collision with default.json). View output ends with [update] (yellow) and [delete] (red) buttons.
9.3 /mossman project update p1 {allowNonMembers:false} Updated project p1 · no SNBT error
9.4 /mossman project config role setpermission p1 Default VIEW_PROJECT GRANT twice in a row First call succeeds (no Collection is empty). Second errors: role 'Default' already has VIEW_PROJECT at GRANT.
9.5 /mossman project config role setpermission p1 Default VIEW_TICKETS INHERIT twice First succeeds. Second errors: role 'Default' already has VIEW_TICKETS at INHERIT.
9.6 Create a role, config role setpermission p1 R EDIT_TICKETS DENY, then config role order p1 R <last>. Assign to a Member, have them attempt to edit a ticket. Edit is denied (higher-index role denies overrides lower-index grants from Editor/Default). config role view p1 R shows EDIT_TICKETS: DENIED.
9.7 /mossman project config role setpermission p1 R EDIT_TICKETS GRANT on a role that already denies it Succeeds — denial is cleared, grant is added (single command flips the state).
9.8 /mossman project config status delete p1 TODO "In Progress" Deleted status TODO (tickets moved to In Progress). Tab-completion suggests remaining statuses for the replacement argument.
9.9 Create tickets 1, 2, 3. Delete #3. Create another ticket. New ticket number is #4 (not #3 — counter never reuses).
9.10 /mossman project view p1, click [update] Chat box prefilled with /mossman project update p1 {} (suggest, not run).
9.11 /mossman project list, click [view] on a row Command runs immediately (RUN_COMMAND), full project view appears.
9.12 /mossman project config role view p1 Default, click any [delete] or destructive button All destructive buttons use SUGGEST_COMMAND (chat prefilled, never auto-run).

Not covered

  • Permission enforcement under non-owner roles — needs at least three players or an /op / /deop workflow.
  • Offline-player targets in role assign/unassign — those still use EntityArgument.player(). The project update {owner:"…"} and ticket update {assignee:"…"} patches accept a UUID string so an offline player can be referenced by UUID when needed.
  • Offline-aware name resolution for owner/assignee by name — only currently-online players are reachable by name.
