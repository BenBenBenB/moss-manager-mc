Moss Manager — Manual test plan

Check off each row as you verify it. State persists in your browser's localStorage under the key mossman-test-plan-v2.

Setup

  1. Run ./gradlew :fabric:runClient from the repo root.
  2. Create a new single-player world with cheats enabled.
  3. World folder default: run/saves/<world-name>/. Project files land at <world>/mossmandata/projects/<id>.json.
  4. You no longer need to look up UUIDs. Role/status/type commands take names; ticket commands take per-project integers (visible in /mossman show). Tab-completion suggests every valid value from the current project — exercise it as you go.

Optional: launch a second client on the same LAN (Fabric: Open to LAN, then connect from a separate client) for the multi-player rows below. All other commands work solo.

Successful commands print white confirmation text in chat (sendSuccess); failures print red error text (sendFailure).

Round 0 — Tab-completion sanity check

#ActionExpected
0.1 Type /mossman and Tab Suggests every top-level subcommand: create, list, delete, rename, owner, nonmembers, show, role, status, type, ticket
0.2 Type /mossman role update and Tab (with at least alpha created — do row 1.2 first) Project ID dropdown shows alpha with the project name in the tooltip
0.3 Type /mossman role update alpha and Tab Suggests Admin, Editor, Viewer, Everyone (case-insensitive prefix match works too)

Round 1 — Project commands

#CommandExpected
1.1 /mossman list No projects you can view.
1.2 /mossman create alpha My Demo Created project alpha  ·  alpha.json appears in mossmandata/projects/
1.3 /mossman create alpha Dup project already exists: alpha
1.4 /mossman list alpha — My Demo
1.5 /mossman show alpha Header line, then Owner: <your player name> (hover the name to see your full UUID), Allow non-members: true, Roles: 4, Statuses: 3, Types: 4, Tickets: 0
1.6 /mossman rename alpha Renamed Demo Renamed alpha to Renamed Demo  ·  /mossman list shows new name
1.7 /mossman nonmembers alpha false Non-member access on alpha: false  ·  /mossman show reflects flag
1.8 /mossman nonmembers alpha true Non-member access on alpha: true
1.9 /mossman owner alpha <OtherPlayer> Transferred alpha to <OtherPlayer>. You may lose admin access.

Don't delete alpha yet — Rounds 2–5 need it.

Round 2 — Role commands

Targeting by name. Tab-completion suggests existing roles after you type the project ID.

#CommandExpected
2.1 /mossman role create alpha {name:"Reviewer", color:0xFFAA00, permissions:["VIEW_PROJECT","VIEW_TICKETS"]} Created role Reviewer
2.2 /mossman role create alpha {color:1} role create requires 'name'
2.3 /mossman role update alpha Reviewer {name:"Senior Reviewer"} Updated role Reviewer — name changes to "Senior Reviewer", color preserved (verify with another /mossman show or by inspecting JSON)
2.4 /mossman role update alpha "Senior Reviewer" {color:0xFF00FF} Updated role Senior Reviewer — color changes; name preserved. Quoted name needed because of the space.
2.5 /mossman role permissions alpha "Senior Reviewer" {permissions:["VIEW_PROJECT","EDIT_TICKETS"]} Set 2 permission(s) on role Senior Reviewer
2.6 /mossman role permissions alpha Editor {permissions:["BOGUS"]} unknown permission 'BOGUS' in 'permissions'
2.7 /mossman role reorder alpha ["Admin","Senior Reviewer","Editor","Viewer","Everyone"] Reordered 5 role(s). Everyone (default role) must stay last. Reorder takes an SNBT list, so multi-word names like "Senior Reviewer" work without renaming.
2.8 /mossman role delete alpha Reviewer Deleted role Reviewer
2.9 /mossman role assign alpha Editor <OtherPlayer> Assigned Editor to <OtherPlayer>
2.10 /mossman role unassign alpha Editor <OtherPlayer> Unassigned Editor from <OtherPlayer>

Round 3 — Status commands

Defaults are TODO, "In Progress" (needs quoting), Done.

#CommandExpected
3.1 /mossman status create alpha {name:"Review", textColor:0xFFFFFF, backgroundColor:0x6B21A8} Created status Review
3.2 /mossman status update alpha Review {name:"Awaiting Review"} Updated status Review — name changes; colors preserved
3.3 /mossman status update alpha "Awaiting Review" {backgroundColor:0x000000} Updated status Awaiting Review — only bg changes; name + textColor preserved
3.4 /mossman status reorder alpha ["TODO","Awaiting Review","In Progress","Done"] Reordered 4 status(es) — multi-word names like "In Progress" work directly inside the SNBT list.
3.5 /mossman status delete alpha Review TODO Deleted status Review — any tickets that were on Review get moved to TODO (covered in Round 5)

Round 4 — Type commands

Defaults are Bug, Feature, Task, Chore. Parallel to status.

#CommandExpected
4.1 /mossman type create alpha {name:"Spike", textColor:0xFFFFFF, backgroundColor:0x444444} Created type Spike
4.2 /mossman type update alpha Spike {name:"Investigation"} Updated type Spike
4.3 /mossman type reorder alpha ["Bug","Feature","Task","Chore","Investigation"] Reordered 5 type(s)
4.4 /mossman type delete alpha Spike Task Deleted type Spike

Round 5 — Ticket commands

Tickets are addressed by per-project integer (#1, #2, …) once created. Use /mossman show alpha to list them; tab-completion on the ticket arg shows each number with the title in the tooltip.

#CommandExpected
5.1 /mossman ticket create alpha {title:"First bug"} Created ticket #1 — uses first status, first type, no assignee
5.2 /mossman ticket create alpha {} ticket create requires 'title'
5.3 /mossman ticket create alpha {title:"Big feature", description:"detailed desc"} Created ticket #2 (number auto-increments; gaps preserved across deletes)
5.4 /mossman show alpha Tickets section shows #1 — First bug and #2 — Big feature
5.5 /mossman ticket update alpha 1 {title:"Renamed"} Updated ticket #1 — description preserved
5.6 /mossman ticket update alpha 1 {description:"new desc"} Updated ticket #1 — title preserved
5.7 /mossman ticket status alpha 1 Done Moved ticket #1 to Done
5.8 /mossman ticket type alpha 1 Bug Set ticket #1 type to Bug
5.9 /mossman ticket delete alpha 1 Deleted ticket #1. Note: creating another ticket now jumps to #3 — numbers don't get reused.
5.10 /mossman ticket assign alpha 2 <OtherPlayer> Assigned ticket #2 to <OtherPlayer>

Round 6 — Project delete & persistence

#StepExpected
6.1 /mossman delete alpha Deleted project alpha  ·  alpha.json removed from disk  ·  /mossman list empty
6.2 Quit, restart world, rejoin /mossman list still empty (cache rebuilt from empty disk)
6.3 /mossman create beta Persist Test, then quit + rejoin /mossman list shows beta — Persist Test (loadAll on SERVER_STARTED)
6.4 Create 3 tickets, delete #2, restart, then:
/mossman ticket create beta {title:"after restart"}		 New ticket gets #4, not #2 — numbers persist through restart and never reuse.

Round 8 — Cross-client sync (multi-player)

Two clients connected to the same integrated server via LAN.

#Action on client AExpected on client B
8.1 /mossman create gamma G Client B's /mossman list now includes gamma
8.2 /mossman delete gamma Client B's /mossman list no longer shows gamma (RemoveProjectS2C broadcast)
8.3 A creates a project while B is offline; B then joins B's /mossman list shows the project (PLAYER_JOIN snapshot path)

Not covered

  • Permission enforcement under non-owner roles — needs at least three players or an /op / /deop workflow.
  • Offline-player targets for role assign / ticket assign / owner — current commands use EntityArgument.player(), which requires an online target.
  • Offline-aware owner-name resolution in show — owner who isn't currently online displays as a short UUID prefix; the hover still shows the full UUID.
